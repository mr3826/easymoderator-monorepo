# 🧠 ORCHESTRATION MODEL (NEW CORE SYSTEM)

Growth OS must be executed using a **multi-agent architecture with a central Orchestrator Agent (OA)**.

## 1. Orchestrator Agent (OA) — PRIMARY CONTROL PLANE

The Orchestrator Agent is responsible for:

- interpreting the phase goal
- decomposing work into sub-tasks
- assigning tasks to worker agents
- resolving conflicts between agents
- merging outputs into a final implementation plan
- enforcing phase boundaries
- ensuring repository evidence compliance
- approving final code changes

👉 **ONLY OA can decide what gets implemented**

---

## 2. Worker Agents (Specialized Execution Units)

Worker agents are stateless executors assigned by OA.

### Core Worker Agents:

### 🧩 Spec Miner Agent

- extracts current system behavior from repo
- maps existing implementation
- produces evidence reports

### 🏗 Architecture Agent

- designs domain models
- proposes system structure
- ensures scalability + boundaries

### ⚙️ Backend Agent

- implements APIs, services, DB logic
- modifies backend safely

### 🎨 Frontend Agent

- implements UI, state, dashboards

### 🧪 Test Agent

- writes unit/integration/E2E tests
- validates regression safety

### 🔐 Security Agent

- validates RBAC, auth, data exposure risks

### 📊 Analytics Agent

- builds metrics, funnels, dashboards

### 🤖 AI Agent (optional)

- handles AI-assisted logic only when required

---

## 3. Orchestration Rules

### RULE 1 — No direct execution

Worker agents NEVER modify code directly without OA approval.

### RULE 2 — Evidence first

All agents must base output on repository evidence.

### RULE 3 — Parallel execution allowed

OA may run multiple agents in parallel for:

- discovery
- analysis
- validation

### RULE 4 — Merge gate required

All outputs must pass through OA merge step.
