## Corrective source review

The worker ownership defect was traced through the ordinary backend import chain: `server.js` loads the app and routes; the notification controller imports QueueManager; its singleton previously created BullMQ Workers on module import. Therefore `START_EMBEDDED_WORKERS=false` did not prevent the API container from consuming jobs. A running rehearsal confirmed that a synthetic no-send canary completed after the dedicated worker was stopped.

Commit `6d6bc1dd056e09202b97d05e81f20308b15109ab` makes QueueManager imports passive and starts consumers explicitly in the dedicated worker or the explicitly enabled embedded-worker path. The dedicated worker waits for BullMQ readiness before advertising ready; Worker reuse prevents duplicate construction. The regression suite passed 4 tests after the change. On the corrected runtime, the canary stayed waiting with the dedicated worker stopped and completed once when it started. The new code also fixes the Growth healthcheck address to the IPv4 loopback used by its Nginx listener.

The broader provider and product limitations remain: `/health/detailed` can call an embedding provider when invoked, so it was not used; customer-photo extraction can fall back from Gemini to OpenAI; text-only RAG order selection remains uncalibrated; and Inbox outage visibility remains incomplete. No live provider request was made.
