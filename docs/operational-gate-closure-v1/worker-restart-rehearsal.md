# Operational Gate Closure V1 — signed webhook worker restart

This optional extension proves durable acceptance of one synthetic Meta-shaped
inbound event while the dedicated queue worker is stopped, then proves worker
consumption and authenticated Shop B Inbox visibility after restart. The API
remains `NODE_ENV=production`; the only POST target is API loopback inside the
backend container. The closure Compose network remains internal/no-egress.
The signer uses the closure-only `META_APP_SECRET` in memory and never prints
the secret or signature. No provider channel token is created or used.

## Preconditions

- Complete the primary authenticated E2E in
  `authenticated-browser-e2e.md` first, while the seed still has no connected
  Meta channel. The existing seed intentionally refuses any connected Facebook
  channel on either fixture shop.
- Use the exact isolated closure Compose project and its generated closure-only
  env file, with `CLOSURE_DB_NAME=easymod_ops_gate_e2e` and the internal
  `postgres` database host. Keep `OPS_E2E_PASSWORD` and the external loopback

- Shop B must remain in effective `MANUAL` reply mode. The setup helper refuses

- Use a fresh run ID per attempt. The rehearsal creates only the synthetic
  `OPS_E2E_PAGE_B` channel and one message addressed to the existing synthetic
  Shop B buyer `ops-gate-buyer-b`.

## Run procedure

Run these commands from the WSL worktree root. The environment-file path is
already generated by the closure setup; this procedure never prints it or its
contents.

The helper POSTs `object: "page"` with `entry[].id` equal to the synthetic Page
ID and one `messaging[]` event whose sender is the seeded Shop B buyer, recipient
is the synthetic Page, and `message.mid` is unique per run. It signs the exact
JSON bytes with HMAC-SHA256 and sends `x-hub-signature-256: sha256=<hex>` to
`POST /api/webhooks/meta`. The GET webhook verification token is not used for
this POST path.

```sh
dc() {
  docker compose --project-name easymod-operational-gate-closure-v1 \
    --env-file "$CLOSURE_ENV_FILE" \
    -f docs/operational-gate-closure-v1/compose.yml "$@"
}
harness() {
  dc exec -T -e OPS_E2E_SEED_CONFIRM=SEED_LOCAL_OPS_E2E_ONLY \
    -e OPS_E2E_PROJECT_CONFIRM=easymod-operational-gate-closure-v1 \
    backend node scripts/operational-gate-closure-v1/worker-restart-harness.js "$@"
}

# Baseline must pass before the synthetic connected Page is introduced.
cd EasyMod-frontend
npx playwright test \
  --config=playwright.operational-gate-closure.config.ts \
  tests/operational-gate-closure-v1/authenticated-tenant-journey.spec.ts
cd ..

# Add the one null-token, synthetic Shop B routing channel.
harness setup

# Stop only the dedicated consumer. Confirm it is exited before posting.
dc stop worker
dc ps -a worker

RUN_ID="ops-$(date -u +%Y%m%dT%H%M%SZ)-$$"

# Sign exact JSON bytes inside the API container and POST to its loopback API.
harness post "$RUN_ID"

# Require durable QUEUED state and a held delayed/waiting BullMQ job before
# restarting the worker. Capture only the synthetic queue job ID from JSON.
QUEUE_JOB_ID="$(harness inspect-queued "$RUN_ID" \
  | node -e 'process.stdout.write(JSON.parse(require("fs").readFileSync(0, "utf8")).queueJobId)')"

# Restore the dedicated worker and wait at most 90 seconds for exact settlement.
dc start worker
dc ps -a worker
harness wait-processed "$RUN_ID" "$QUEUE_JOB_ID" 90000

# Authenticated browser confirms that the same Shop B Inbox shows the message
# and the MANUAL worker run produced no AI suggestion.
cd EasyMod-frontend
OPS_E2E_WEBHOOK_RUN_ID="$RUN_ID" npx playwright test \
  --config=playwright.operational-gate-closure.config.ts \
  tests/operational-gate-closure-v1/authenticated-webhook-worker-restart.spec.ts
cd ..

# Disconnect the exact synthetic Page and detach only the seeded B records.
harness cleanup
```

The harness prints a small JSON receipt containing only synthetic IDs, states,
counts, and booleans. Save the `post`, `inspect-queued`, `wait-processed`, and
browser-test outputs as the rehearsal receipt. The inspection modes check the
event's exact receipt and BullMQ job; `/health/detailed` queue totals alone are
not event-level evidence.

## Expected evidence

- The signed `POST /api/webhooks/meta` returns HTTP 200.
- Before worker restart, the receipt is `QUEUED`, is bound to Shop B and the
  synthetic Page, retains encrypted replay bytes and a BullMQ job ID, and that
  exact job is delayed or waiting. Exactly one customer message exists.
- After worker restart, that job is `completed`; its receipt is `PROCESSED`,
  with its replay bytes and queue-job binding cleared.
- The Shop B authenticated browser sees the exact synthetic inbound in the
  selected Inbox thread. No AI row or provider acknowledgement is created
  after that inbound; Shop B stays `MANUAL`.
- The harness does not flush Redis, truncate tables, or delete the receipt or
  message. Cleanup only disconnects the null-token synthetic Page and clears
  that Page link from the seeded Shop B buyer/thread. It refuses to run while
  any receipt for that Page remains in a nonterminal state.

## Failure handling and limits

If `inspect-queued` fails, do not start another webhook or reuse the run ID;
retain the isolated state for diagnosis. If the worker wait times out or a
receipt reaches a failed state, stop the rehearsal and preserve its DB/Redis
evidence. Do not run `docker compose down -v`, seed truncation, or `FLUSHDB`.

Starting the dedicated worker also starts its scheduled consumers. Keep this
run inside the isolated closure project. Shop B's MANUAL gate returns before
LLM generation/send, its synthetic Page has no token, and the Compose network
has no egress. This is local signed-ingress and queue-recovery evidence; it is
not live Meta delivery, provider-send evidence, or inference validation.
